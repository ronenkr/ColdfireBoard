# USB bootloader for the SafeQ MCF52254 board

Everything goes through the board's own micro-USB port: uploading, verifying,
starting the app, and the debug console. The board shows up as a USB serial
port (CDC-ACM, `/dev/ttyACM*`) and needs no driver.

| Mode       | USB ID      | Product string       |
|------------|-------------|----------------------|
| bootloader | `1209:0001` | `CF52254 bootloader` |
| app        | `1209:0002` | `CF52254 app`        |

## Daily use

```
cd fw && make APP=1                        # build the app, linked at 0x4000
../.venv/bin/python ../boot/cfboot.py flash fw.bin    # reboot -> upload -> verify -> run
../.venv/bin/python ../boot/cfboot.py console         # app/bootloader output, Ctrl-C quits
```

Other commands: `info`, `verify app.bin`, `read out.bin [len]`, `run`, `boot`.

## How the board gets into the bootloader

- **The app uses the USB services:** `cfboot.py` opens the port at 1200 baud
  and drops DTR (the "1200-baud touch"). The board acknowledges, detaches, and
  reboots into the bootloader. This works with no user action.
- **The app doesn't use USB, or it hung:** start `cfboot.py`, then plug in or
  power-cycle the board. After a reset the bootloader waits 1 s past USB
  enumeration, or 8 s if no host enumerates it, before starting the app. An
  `I` command from `cfboot.py` during that window keeps it in the bootloader.
- **No valid app is installed:** the bootloader stays active.

## Writing an app

- Link at `0x4000` with RAM below `0x2000E000`; `fw/` does both with `make APP=1`.
- Include `boot/cfboot.h`, then call `CFBOOT_SVC->usb_init()` once and
  `usb_poll()` every few ms.
- Use `write()`, `read()` and `connected()` for the console. `fw/main.c` is
  an example.
- Keep fsys at 48 MHz. The bootloader configures the PLL that way, and USB
  depends on it.

## Memory map

| Range                   | Contents                                                  |
|-------------------------|-----------------------------------------------------------|
| `0x00000–0x03FFF` flash | bootloader; CFM config at `0x400`, service table at `0x418` |
| `0x04000–0x7FFFF` flash | application                                               |
| `0x20000000–0x2000DFFF` | application RAM                                           |
| `0x2000E000–0x2000FFFF` | bootloader USB state, BDT, RAM flash routines             |

## Testing

`.venv/bin/python boot/selftest.py` runs 39 hardware checks. It needs the
RP2040 on CON5 for resets and the square-wave check. The checks cover:

- bootloader protection and integrity;
- a full 496 KB write with byte-for-byte read-back;
- 10 update cycles started from a running app;
- idle power-ups;
- recovery from an app with no USB and from an app that crashes;
- an interrupted upload followed by power loss.

The last runs, on 2026-10-15, passed 39/39 twice, plus 30/30 idle power-ups.

The test apps in `build/` are built from `fw/main.c` and `fw/hwtest.c`:

```sh
cd fw
make APP=1                                  && cp fw.bin ../build/app_usbdemo.bin
make APP=1 PROG=hwtest                      && cp fw.bin ../build/app_hwtest.bin
make APP=1 EXTRA=-DNO_USB                   && cp fw.bin ../build/app_nousb.bin
make APP=1 EXTRA="-DCRASH -DNO_USB"         && cp fw.bin ../build/app_crash.bin
```

Run `make clean` between these builds. `build/big_random.bin` is generated by
the self-test itself.

## Notes

- **Updating the bootloader itself** still uses EzPort through the RP2040:
  `ezport/ezflash.py flash boot/boot.bin --fsys 12000000`. That bulk-erases
  the chip, so the app has to be re-uploaded afterwards. The bootloader never
  writes below `0x4000`, and it does not use CFMPROT, because CFMPROT would
  block EzPort recovery.
- **Debug log:** off in normal builds. `make DEBUG=1` sends a compact USB
  event log on UART1 TX (MCU pin 19, CON5-7, 115200 8N1; the UART runs on
  fsys = 48 MHz). Read it with the RP2040: `ezport/ezflash.py console`.
- **Leftover watchdog:** a board that still has its original SafeQ firmware
  has the backup watchdog armed, and it stays armed after that firmware is
  erased (its registers are write-once; only a power-on reset clears them), so
  the chip resets every few hundred ms. The bootloader feeds it (`bwt_service()`
  in `boot.h`): at start-up, in `usb_poll()`, between page erases, during CRCs
  and the app hand-over. Apps that run on such a board must reach
  `usb_poll()` soon after start and call it regularly. Unplugging the board
  disarms it. `make DEBUG=1` prints the reset cause (`rsr 80` = backup
  watchdog) and the watchdog registers; `fw/bwtarm.c` arms the watchdog for
  testing. Note that WCR is a 16-bit register: the enable bit is in the byte at
  `0x40140001`.
- **Apps and interrupts:** VBR must be 1 MB aligned, so apps copy their
  vector table to SRAM at `0x20000000` (`fw/start.S`) and install handlers
  there. An unexpected exception in an app does a soft reset, which falls back
  to the bootloader.
- **Linux hub autosuspend:** this laptop's internal USB hub (`1-1`) suspends
  with a 0 ms delay and then misses newly attached devices. `cfboot.py` keeps
  the hubs awake from a background thread. Opening a suspended hub can take
  seconds, and the boot window is only about 1 s. For a permanent fix:
  `echo on | sudo tee /sys/bus/usb/devices/1-1/power/control`
